# job-intel-agent · 大模型岗位情报站

找大模型方向的工作，要一个个翻招聘网站，每条 JD 几百上千字，翻完也记不住几个。

这个项目把这件事变成「直接提问」：自动采集大模型方向的真实招聘岗位，存进本地数据库，建好语义索引，然后你问"我在深圳找 Agent 开发岗，会 Python 和 LangGraph"，它不只是把岗位列给你——它会**先问清楚你的条件、再逐条算匹配度、指出你差哪项技能、把最该投的排在最前面**，每个结论都能点回 JD 原文核对。

全流程一条龙，五个模块各自独立：**采集 → 检索 → 智能体 → 评测 → 服务**。

## 它和通用编程 Agent 有什么不同

Codex / OpenCode 那类通用 agent 强在「给我代码我改」——它们的工具是文件读写和命令执行。
但「择岗」这件事需要的完全是另一套能力：

| | 通用编程 Agent | 本项目（择岗顾问） |
|---|---|---|
| 输入 | 代码 / 报错 | 用户的模糊诉求（"帮我看看有什么岗"） |
| 关键难点 | 读懂代码 | **识别缺失的条件并主动追问** |
| 工具 | 读写文件、跑命令 | 匹配度打分、技能差距分析、条件过滤、岗位对比 |
| 结论形态 | 改好的代码 | 排好序的推荐 + 可解释的评分依据 |
| 失败代价 | 代码跑不通 | 推荐错了，用户白投简历 |

差别不在"用了哪个模型"，而在**专业动作的沉淀**：把"择岗该怎么决策"写成可复现的代码，
而不是每次让模型自由发挥。这正是这个项目要展示的东西。

## 先跑起来看看

不用配任何 Key，两条命令就能在浏览器里用起来：

```bash
git clone https://github.com/JonathanQUANLEE/job-intel-agent.git
cd job-intel-agent
python start.py          # 自动装依赖、建数据、起服务
```

浏览器会自动打开 http://127.0.0.1:8000，直接提问或浏览岗位。

> Windows 双击 `start.bat`、macOS/Linux 跑 `bash start.sh` 效果一样。

**没有 API Key 也能用吗？** 能。项目内置本地检索降级通道（BM25 + 中文分词 + 城市加权），
没配 Key 时自动切过去，照样能搜出岗位，只是少了 AI 的分析点评。
想要完整的"技能差距对比"体验，再配 Key 不迟（见下文）。

## 它是怎么工作的

```
腾讯招聘 公开接口（列表 + 详情两段式）
      │
      │  crawler  采集：requests 拉接口，列表拿岗位、详情补全完整 JD
      │            （职责 + 任职要求），清洗成统一格式，以 job_id
      │            为主键写入 SQLite，重复运行自动去重 + 补全
      ▼
SQLite · jobs 表（当前 428 条真实岗位，全部带完整 JD，平均 637 字）
      │
      │  rag      建索引：JD 按句子边界切成约 900 字的片段，
      │           BGE-M3 转成 1024 维向量，存进同一库的 jd_chunks 表
      ▼
提问时的决策流程（LangGraph 编排，每一步都是图上的一个节点）
      │
      │  agent
      ▼
   intake ──缺城市/方向──→ clarify ──→ 追问，等用户下一轮
     │                                    （画像跨轮累积，不丢条件）
     └─条件够──→ recall ──→ evaluate ──┬─结果弱──→ refine ──┐
                            ▲          │        （放宽条件补搜，   │
                            └──────────┼─────────  上限 2 次护栏）┘
                                       │
                                       └─结果够──→ compose ──→ 回答

   每个节点的产出都进 trace（推理轨迹），前端渲染成时间线：
   用户能看到 agent 抽了什么条件、检索了多少候选、谁排第一、差哪项技能。
```

**三个值得说的设计取舍：**

1. **为什么先追问再检索？** 用户说"帮我推荐些岗位"时，条件和方向都是空白。
   这时候检索出来的东西对他毫无价值——不是数据问题，是**信息不足**。
   所以缺「城市」或「方向」这两个硬条件时，agent 直接追问，一次都不检索。
   软条件（经验、薪资）缺失则不追问，避免第一轮就把用户问烦。

2. **为什么打分是确定性代码而不是交给模型？** 择岗的核心结论（谁排第一、差哪项技能）
   不能让模型自由裁量——它今天说 A 好明天说 B 好，产品就没法用。
   所以把"判断"沉淀成规则代码（可复现、可测试、可回归），把"表达"交给模型：
   模型拿到算好的骨架后只做润色，且被明确要求**不得增删任何岗位、分数或技能**。
   这个分工是这个项目最重要的设计取向。

3. **为什么方向打分区分「标题命中」和「正文提及」？** 早期版本只看正文有没有出现
   "agent"，结果"视频生成研究员"（JD 里提了一句"与 agent 协作"）也混进了 Agent 岗推荐。
   改成标题命中给满分、仅正文提及只给 40% 并标注"弱对齐"后，
   排序立刻合理了。这是被真实数据教的一次教训，也是评测集能抓住的问题。

为什么用语义检索而不是关键词搜索？"熟悉 PyTorch"和"掌握深度学习框架"关键词对不上，但意思相近，向量能匹配上。这正是 JD 匹配场景里最需要的能力。

## 快速开始（手动版）

**准备**：Python 3.10+。想要语义检索 + AI 分析，再准备一个硅基流动 API Key
（到 https://console.siliconflow.cn 注册即送额度，把全流程跑一遍只花几分钱）。

**1. 安装**

```bash
pip install -r requirements.txt
```

**2. 导入数据**（仓库自带数据快照，先导入即可用）

```bash
python -m seed                      # 从 data/jobs_export.csv 导入 428 条岗位
```

**3. 起服务**

```bash
python -m api
# 打开 http://127.0.0.1:8000
```

**4. 想要语义检索 + AI 分析？配 Key**

项目根目录建一个 `.env` 文件，写入一行：

```
SILICONFLOW_API_KEY=sk-你的Key
```

代码自己会读这个文件，不需要装 python-dotenv，也不会把 Key 提交进仓库。配好后重建索引：

```bash
python -m rag --index      # 切块 + 向量化入库，逐条打印进度
```

## 采集更多岗位

```bash
python -m crawler --source tencent --keyword "大模型" --max-pages 3
python -m crawler --source tencent --keyword "Agent" --max-pages 3
```

运行完会打印类似这样的结果：

```
[tencent] 原始 30 条 → 有效 30 条 → 新增 28 条（重复/跳过 2 条）
```

默认会调详情接口补全完整 JD（含任职要求），慢一些但信息量差一个数量级。
想快就用 `--no-detail` 跳过。

重复运行不会产生重复数据：job_id 是主键，插不进去就跳过；
而且如果这次拿到了更完整的 JD，会自动把旧的正文更新掉。

```bash
python -m crawler --stats                    # 各来源入库条数
python -m crawler --sample 5                 # 抽 5 条看看
python -m crawler --export data/jobs.csv     # 导出 CSV 快照
```

## 四种用法

| 命令 | 是什么 | 什么时候用 |
|---|---|---|
| `python start.py` | 一键起 Web 界面 | **推荐**，浏览器里问答 + 浏览岗位 |
| `python -m rag --ask "问题"` | 一次检索、一次回答，带来源列表 | 命令行快速看效果 |
| `python -m agent --ask "问题"` | 智能体模式，模型自主决定查什么、查几轮 | 想看 Agent 的决策过程 |
| `python -m api` | FastAPI 流式问答服务 | 想集成到别的产品里 |

## Web 界面

单文件 HTML（`api/index.html`），零构建、零前端依赖，功能包括：

- **对话式提问**：流式打字机输出，回答里的每个结论都带来源编号
- **来源卡片**：检索到的岗位以卡片展示，标注城市/事业群/经验要求，点击直达官网 JD
- **岗位浏览**：按关键词 + 城市筛选，点开看完整 JD，一键复制
- **多端适配**：手机/平板/桌面都能正常用
- **离线降级提示**：没配 Key 时界面顶部明确标注"本地检索"模式

## API 接口

服务起来后 http://127.0.0.1:8000/docs 有交互式文档。

| 接口 | 说明 |
|---|---|
| `GET /` | Web 聊天界面 |
| `POST /ask` | SSE 流式择岗（含推理轨迹 + 结构化推荐） |
| `GET /jobs` | 岗位列表（keyword + location 筛选） |
| `GET /jobs/{id}` | 单个岗位完整 JD |
| `GET /meta` | 岗位总数、城市分布、是否有 Key |
| `GET /health` | 健康检查 |

`POST /ask` 返回 SSE 事件流，前端按类型分流：

| 事件 | 内容 |
|---|---|
| `meta` | 本次走的检索通道（vector/offline） |
| `profile` | 从问题里抽出的择岗条件（城市/方向/技能…），让用户能当场纠正理解偏差 |
| `plan` | **推理轨迹**，逐步推送：抽槽 → 检索 → 打分 → 成稿 |
| `clarify` | 信息不足，agent 在追问（前端高亮 + 留住画像给下一轮） |
| `recommendations` | **结构化推荐**：每条含匹配分、档位、命中/缺失技能、评分依据 |
| `gap` | 技能差距汇总（该补什么，按出现频次排序） |
| `token` | 回答正文，逐段推送，打字机效果 |
| `done` / `error` | 结束 / 出错 |

请求体支持 `profile` 字段实现多轮：

```bash
curl -N -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "再帮我看看北京的", "profile": {"city": "深圳", "direction": "agent"}}'
```

为什么做流式？生成完整回答要好几秒，流式把等待感从"全部生成完"降到"第一个字出来"，这是所有 AI 产品的标配体验。

为什么要把推理轨迹也推给前端？因为择岗顾问的价值不只是给结论，还要说清"为什么是这几个"。
用户看到 agent 抽了什么条件、检索了多少候选、谁排第一、差哪项技能——理解错了能当场纠正，
信任感也就建立了。这是通用编程 agent 给不了的透明度。

## 评测：怎么知道它答得准不准

评测分两层，各管一段——**召回**回答"找得到吗"，**决策**回答"行为对不对"。

### 第一层：召回评测

30 条人工标注的评测集在 `evals/dataset.json`，从两个维度打分：

```bash
python -m evals --skip-faithful   # 只跑召回，不耗对话额度
python -m evals                   # 召回 + 忠实度全量
```

- **召回**：该找到的岗位有没有找到、排在第几名。hit@5 衡量"前 5 名里有没有正确答案"，MRR 衡量"正确答案排得有多靠前"。
- **忠实度**：回答里提到的岗位、城市、技能要求，是不是都能在检索片段里找到依据。由 LLM 当裁判逐条判定，判不了按不忠实计，从严。

评测脚本和命令行、API 走同一套检索策略（`rag.retriever.retrieve()`），所以数字对产品行为有解释力。**评测本身支持离线**：没有 Key 时自动降级 BM25，忠实度自动跳过——428 岗位库上的结果：

| 检索模式 | hit_rate@5 | MRR |
|---|---|---|
| offline（BM25，无 Key） | 0.70 | 0.50 |
| vector（BGE-M3，有 Key） | 配置 Key 后自行跑一遍对比 | 同左 |

离线基线 0.70 说明纯关键词检索已经能用；向量模式的价值在"同义改写"型提问上——比如"数据科学或数据分析岗位"，字面词对不上、语义才对得上。

### 第二层：决策质量评测

召回高不等于体验好。一个"召回 100% 但从不追问、把北京岗位推给深圳用户"的 agent，
召回指标一样漂亮，却完全没法用。所以另建一套 **15 条行为契约**（`evals/decision_set.json`）：

```bash
python -m evals.decision
```

每条用例声明一组确定性断言，覆盖这些行为：

| 检查项 | 例子 |
|---|---|
| 追问时机 | 缺城市/方向时必须追问；只缺城市时不能重复问方向 |
| 条件继承 | 上一轮说的"深圳"，下一轮不能被丢掉 |
| 硬条件生效 | 查深圳时 Top1 必须是深圳岗位 |
| 排序正确 | 推荐必须按匹配分降序 |
| 结果完整 | 每条推荐必须带 job_id / 分数 / 档位 / 评分依据 |
| 轨迹完整 | 推理轨迹必须含"画像识别→检索→打分"三个可解释步骤 |
| 词表精度 | 动词"推荐"不能被误判成"推荐算法"方向 |

**全部用规则断言、不依赖 LLM 判卷**——能用规则精确判断的行为就不用模型，
既省额度又避免引入不确定性。这套评测当场抓到过两个真实 bug：
①"城市不限"没被识别（导致该出结果时反而追问）；②方向只做正文关键词匹配
（导致视频生成岗混进 Agent 推荐）。修完从 14/15 到 15/15。

这 15 条同时被包进 pytest，`pytest` 一跑就能拦住"行为回退"，
比人工记得去跑评测可靠。

## 项目结构

```
start.py / start.bat / start.sh   一键启动
seed.py               从 CSV 快照导入数据
crawler/              采集：http_client 重试退避 / sources 列表+详情两段式
                              / normalize 清洗 / storage 入库与查询
rag/                  检索：chunker 句子边界切块 / embedder BGE-M3 嵌入
                              / store 向量存取 / offline BM25 离线降级
                              / retriever 统一检索入口（自动降级）
                              / llm 带引用回答
agent/                智能体：profile 偏好槽位（追问依据）
                              / scoring 匹配打分（可解释）
                              / tools 专业动作（打分/差距/过滤/对比 + Function Calling）
                              / graph LangGraph 决策编排
                              / llm_client 润色（只改表达不改事实）
evals/                评测：dataset.json 30 条召回集 / decision_set.json 15 条行为契约
                              / metrics 纯函数指标 / run_eval 召回 / decision 决策质量
api/                  服务：FastAPI + SSE（含推理轨迹）+ index.html 单文件界面
tests/                离线单元测试（42 个）
data/                 采集数据快照 CSV
jobs.db               SQLite，运行时生成，不入库
```

## 几个设计上的取舍

| 决策 | 为什么 |
|---|---|
| SQLite 单库存岗位和向量 | 几百条规模，少一个组件就少一份部署维护成本；结构化字段和向量同库，事务一致 |
| 检索有离线降级通道 | 用户第一次打开产品时多半还没配 Key，白屏等于劝退；BM25 + 城市加权在几百条规模下完全够用 |
| numpy 暴力余弦，不上向量数据库 | 实测 428 条向量完整检索毫秒级，够用；检索收在 `rag/store.py` 一个函数里，数据量上来换 FAISS，调用方不用改 |
| 采集走"列表 + 详情"两段式 | 列表接口的正文只有百来字且被截断，直接建索引检索质量很差；详情接口才有完整 JD 和任职要求 |
| 数据源插件化 | 一个来源一个函数，normalize 统一格式，新增平台不动主流程 |
| **规则管事实、模型管表达** | 择岗结论（排名、分数、差距）必须可复现，交给确定性代码；模型只润色表达，且被禁止增删事实 |
| **缺硬条件必须追问** | "帮我推荐岗位"时条件和方向都是空白，此时检索结果对用户无价值——不是数据问题，是信息不足 |
| **软条件缺失不追问** | 经验、薪资这类偏好有默认值就行，第一轮就问全所有信息会劝退用户 |
| **方向打分区分标题/正文** | 只看正文关键词会让"视频生成岗"（提了一句 agent）混进 Agent 推荐；标题命中才算强对齐 |
| Agent 设护栏 | 补搜上限 2 次、模型润色失败退模板、工具失败降级为文本反馈——任何一环挂掉都不白屏 |
| 评测分两层 | 召回（找得到吗）+ 决策（行为对不对）。后者用规则断言，能拦住"行为回退"这类召回指标看不出的问题 |
| 前端单文件、零构建 | clone 下来就能改，不用装 node_modules；也方便直接分享 |
